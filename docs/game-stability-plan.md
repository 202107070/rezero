# 게임 정상화 실행 계획

작업 브랜치: `fix/backend-integration-stability`

## 목표와 작업 원칙

기존 게임 규칙과 화면을 유지하면서 자동 저장·복원, 문제 언어, 실제 빌드, 닉네임 중복 방지를 정상화한다. 항목별 수정과 테스트를 통과한 뒤 전체 변경을 통합 테스트한다. 통합 테스트가 통과해야 실제 브라우저에서 전체 게임 흐름을 검증한다. 실패한 검증을 통과로 기록하지 않는다.

- 구현·분리 검증은 맥의 별도 체크아웃과 별도 서버 환경에서 진행한다. 운영 적용은 사용자 진행 승인 이후 별도 버전/백업을 준비해 진행한다. Pi 작업본은 변경하지 않는다.
- 학교에서 새 테스트 디렉터리·별도 포트·별도 DB·별도 Valkey 인스턴스를 사용한다. 테스트에 운영 계정·방·전적을 사용하지 않는다.
- 운영 적용·닉네임 중복 데이터 정리·방화벽 변경은 최종 검토 후 별도로 진행한다. 기존 데이터는 자동 삭제하거나 개명하지 않는다.
- 디자인·캐릭터·친구·채팅·AI 분석·아이템 효과·점수·승패·골드·레이팅 규칙 및 전체 폴더 구조는 변경하지 않는다. 경계 연결에 필요한 최소 변경만 허용한다.
- 작업별 변경 파일·검증 명령·결과·남은 문제를 이 문서에 추가한다. 코드 변경은 항목별로 커밋하며 develop에 직접 반영하지 않는다.

## 최종 서버 확정 — 2026-11-06

사용자 확정에 따라 학교 컴퓨터 `100.75.215.11`을 최종 게임 서버로 사용한다. Pi는 비교 검증 대상이었으며 운영 배포 대상과 필수 완료 조건에서 제외한다. Pi 부팅 설정 변경·재부팅·전체 게임 재검증은 현재 작업에 필요하지 않다. 아래 Pi 실패 기록은 당시 관찰 사실로 보존한다.

학교의 별도 환경에서 통과한 검증을 기준으로 학교 운영 적용을 준비했다. 프론트 개발 프록시와 환경변수 예시의 기본 대상은 학교 `8080`이다. 별도 테스트는 `VITE_API_PROXY_TARGET=http://127.0.0.1:18082`로 지정한다. 이후 사용자 진행 승인에 따라 `28ea8f6`을 운영 적용했으며 현재 결과는 하단 운영 기록과 별도 보고서를 따른다.

## 단계와 통과 조건

### 0 준비와 기준 검증

1. 브랜치와 변경 여부를 확인한다. 기존 스크립트의 운영 데이터 생성·삭제 여부를 확인한다.
2. 의존성을 격리된 작업 폴더에 준비하고 기존 프론트 빌드·배틀 규칙 테스트 결과를 기록한다.
3. 테스트를 단위·API·DB/Valkey/실행기 통합·브라우저로 나눈다. 저장/실행 서비스는 의존성을 주입할 수 있도록 작게 분리한다.
4. 테스트용 설정은 추적하지 않으며 시크릿을 로그나 문서에 기록하지 않는다.

통과: 기준 실패를 식별하고 이후 실패와 구분할 수 있다.

### 1 자동 저장와 복원

수정 위치: `backend/src/api/build`, `backend/app.js`, `frontend/src/services/battleSessionService.ts`, `sessionStore.ts`, `frontend/src/pages/battle/BattlePage.tsx` 및 필요한 타입.

1. 기존 URL `POST /api/v1/build/session/save`를 인증된 API로 구현한다. `GET /api/v1/build/session/:matchId`로 본인 초안을 조회한다.
2. 경기 존재·진행 여부·참가 자격을 확인한다. 사용자 ID는 인증 토큰에서만 얻는다.
3. Valkey에 경기+사용자별 초안을 저장한다. 저장 버전으로 늦게 도착한 요청이 최신 답안을 덮어쓰지 못하게 한다. 키는 만료 시간을 가진다.
4. 저장 필드는 matchId, currentIndex, codes, blankAnswers, selectedOptions이다. 문제/정답·점수·보상·시간은 클라이언트 입력을 권위 있는 값으로 저장하지 않는다.
5. 복원 시 서버 경기 스냅샷과 남은 시간을 사용한다. 기존 제출 상태를 되돌리거나 시간을 늘리지 않는다.
6. 공통 인증 호출을 사용하되 초안 저장의 일시적인 통신 실패로 전체 앱을 강제 이탈시키지 않는다. 기존 공통 호출의 기본 동작은 유지한다.
7. 브라우저에도 사용자+경기별 초안을 보존한다. 서버 저장 실패와 브라우저 보존을 구분하며 서버 응답 전 saved 처리하지 않는다.
8. 변경을 모아서 저장하고 순차 전송한다. 재시도 횟수/간격을 제한하며 종료·퇴장 시 타이머를 해제한다. 새 입력을 오래된 응답이 덮어쓰지 않도록 한다.
9. 새로고침으로 메모리의 문제 목록이 사라져도 진행 경기 API에서 복원한다. 실제 경기에 임시 예제 문제를 대체 출제하지 않는다.

검증: 토큰 없음 401, 비참가자 403, 없는 경기 404, 종료 경기 쓰기 차단, 정상 저장/조회, 사용자 격리, 오래된 버전 차단, 재시도/타임아웃, 서버 실패 시 saved 금지, 재접속 답안/객관식/문제 위치 복원, 경기 간 격리, 남은 시간 증가 금지.

### 2 문제 언어와 표시

수정 위치: 문제 서비스·문제 응답 DTO·언어별 템플릿 자료·코드 조립 유틸리티. 기존 문제 ID와 운영 데이터는 유지한다.

1. 모든 문제를 읽기 전용으로 분류하여 유형/언어/코드 문법/빈칸/정답 형식의 일관성을 점검한다.
2. 코드 문제에는 언어별 본문과 실행 템플릿을 명시한다. 단순 문자열 치환으로 Java를 Python으로 바꾸는 경로를 실제 경기에서 사용하지 않는다.
3. 검증된 언어 변형만 출제하고, 요청 문제 수가 부족하면 경기 생성 전 명확하게 검사한다. 시작 이후 문제 로드 실패나 임시 문제 출제가 발생하지 않게 한다.
4. 공백/따옴표 등 입력과 실행 템플릿의 표현을 맞춘다. 기존 정답 판정 규칙은 불필요하게 변경하지 않는다.

검증: 지원 언어별 표본 및 전체 자료 감사, 빈칸 수/답 개수 일치, 다른 언어 코드 없음, 객관식/단답/시각 문제 유지, 문제 수 부족 사전 감지, 원본 자료 보존.

### 3 실제 빌드 실행

수정 위치: BUILD API, `backend/src/infra/docker/worker/gameWorker.js`, 실행 설정/전용 이미지, 프론트 빌드 호출부. 미사용 manager/controller를 게임 시작 경로에 다시 연결하지 않는다.

1. 인증·경기 참가·문제 번호·지원 언어를 검증하는 빌드 API를 구현한다.
2. Java/Python/C++ 실제 컴파일/실행과 HTML/CSS 미리보기 처리를 구분한다. 부분 코드에는 검증된 언어별 실행 템플릿을 사용한다.
3. Podman으로 요청별 격리된 실행 작업을 만든다. 쉘 문자열로 소스를 실행하지 않는다. 비루트·네트워크 차단·CPU/메모리/프로세스/실행시간/출력량 한도를 적용한다.
4. 작업별 임시 공간과 설정 경로를 사용한다. 이전 사용자 결과나 동시 요청이 섞이지 않도록 한다.
5. 성공/컴파일 오류/실행 오류/시간 초과/실행 환경 미준비를 구분한다. 환경 미준비를 코드 성공으로 위장하지 않는다.
6. 게임 중 빌드 횟수 정책은 유지하고 중복 요청/재시도로 중복 차감하지 않는다. 프론트의 고정 성공·가상 컴파일러 메시지를 실제 API 결과로 교체한다.

검증: 언어별 정상 출력, 문법 오류, 런타임 오류, 무한 루프, 출력 과다, 동시 사용자, 작업 간 파일 격리, 환경 미준비, 중복 요청, 빌드 횟수, amd64/arm64 실행 환경.

### 4 닉네임 중복 방지

수정 위치: 사용자 가입 오류 매핑·추가 마이그레이션/사전 점검 스크립트. 운영 스키마는 이 단계에서 자동 변경하지 않는다.

1. 기존 닉네임 비교 정책과 DB collation을 확인한다. 동시 가입에서 DB unique 위반을 닉네임 409로 반환한다.
2. 중복 데이터 조회와 unique 인덱스 추가를 분리한 재실행 가능한 마이그레이션을 준비한다.
3. 중복이 발견되면 중단하고 대상 수를 보고한다. 삭제·개명하지 않는다.

검증: 기존 사전 검사, 동시에 동일 닉네임 가입, 대소문자 정책 일치, 기존 중복 시 적용 중단, 이미 인덱스가 있는 학교 DB에서도 안전한 재실행.

### 5 서버별 적용 준비

학교 테스트 체크아웃·별도 DB·Valkey·포트에 같은 커밋을 준비한다. 운영 환경값을 덮어쓰지 않는다. 팀원 Tailscale 접근 범위에 한정한 8080 방화벽 적용/복구 명령과 프론트 프록시 설정을 문서화한다. 실제 운영 방화벽/DB 변경은 검토 전 실행하지 않는다.

검증: 프론트와 백엔드 대상 확인, HTTP/WebSocket 연결, 의존성 사전 점검, 실행기 준비 상태. Pi 비교 검증은 참고 기록이며 최종 서버의 필수 통과 조건이 아니다. 학교 환경을 운영 적용 대상으로 삼는다.

### 6 전체 변경 통합 테스트

단계 1~5의 단위·API 테스트, 프론트 타입/빌드, 별도 DB·Valkey·실행기 테스트를 함께 실행한다. 기존 배틀 규칙과 최종 결과 중복 방지 검증을 포함한다. 운영 데이터에 접근하는 기존 테스트는 별도 환경을 강제하지 못하면 실행하지 않는다.

통과: 필수 테스트 모두 통과. 반복 401/404/500, 실패의 성공 위장, 사용자 데이터 혼합, 중복 보상 없음. 미실행 항목을 명시하고 통과로 취급하지 않는다.

### 7 실제 게임 전체 흐름 테스트

실제 브라우저의 테스트 계정 두 개로 가입/로그인 → 방 생성/입장 → READY → 시작 → 답안 입력 → 실제 빌드 → 중간 저장 → 새로고침/재접속 → 제출 → 관전 → 종료 → 결과/보상 DB 확인 → 로비/다시하기를 진행한다. 객관식·단답·코드 문제, 지원 언어, 네트워크 일시 중단, 동시 제출, 중복 제출을 포함한다.

통과: 화면·API·DB/Valkey·실행 결과가 일치하고 게임 규칙이 유지된다. 증거 화면, 요청 결과, 저장 결과를 시크릿 없이 기록한다. 이후 변경 파일·검증 결과·배포 전 필요한 확인 사항을 정리한다. develop 병합과 운영 적용은 별도 단계이다.

# 학교 운영 서버 추가 언어·이탈 복귀 검증

대상: 학교 운영 8080, 배포 소스 `28ea8f6`. 기존 검증 계정 2개를 사용하며 운영 문제 은행/경기 스냅샷/게임 규칙은 변경하지 않는다. 요청 범위는 테스트와 결과 분석이다.

## 실행 순서와 판정 기준

1. 서비스/프론트 대상/적용 소스를 확인하고 로그 시작 위치를 기록한다.
2. Java와 C++은 실제 코드 문제가 포함된 경기에서 컴파일·출력·횟수, 제출·결과·보상·로비를 확인한다. HTML/CSS는 실제 화면 미리보기·제출·결과·보상을 확인한다. 문제는 원래 무작위 출제를 사용한다.
3. 경기 중 답안 일부/제출/빌드 상태를 만든 뒤 다음 복귀 방식을 구분한다.
   - 동일 탭 새로고침: 같은 경기 ID, 답안/선택, 제출 점수, 남은 시간 감소, 빌드 횟수, 상대 진행 유지.
   - 탭을 닫고 새 탭에서 다시 로그인: 로비에서 진행 경기 진입 경로가 있는지, 서버 초안/제출/횟수가 같은 경기로 복원되는지 확인. 수동으로 경기 URL을 열어 복원되는 경우는 일반 UI 복귀와 별도로 기록.
   - 게임의 나가기 버튼으로 로비 이동 후 같은 방 재입장: 경기가 유지되는지, 퇴장/기권으로 처리되는지 확인. 강제 이탈과 명시적 퇴장을 같은 성공으로 합산하지 않는다.
4. 실패한 경우 화면/응답 코드/서버 상태/관련 로직을 기록하고 임의로 기권·재입장 정책을 변경하지 않는다. 다른 언어의 독립 검증은 계속한다.
5. 마지막에 경기 DB 결과·사용자 보상·로그를 대조하고 브랜치에 증거를 기록한다.

## 판정

브라우저 탭 종료로 로그인이 풀리는 것 자체를 데이터 유실로 판정하지 않았다. 서버 저장은 남아 있지만 재로그인/방 재선택에서 원래 경기로 연결하는 경로가 없다. 단순히 ‘나갔다가 들어와도 된다’고 사용자에게 안내할 수 있는 상태는 아니다.

탭 종료 직전 서버 확인: `battle-9`의 A 초안 currentIndex=1, 두 번째 답 `class`, 제출 점수 100, 첫 문제 buildUsed=1이었다. 새 탭 로그인 후에도 DB 참가 행과 STARTED 방/IN_PROGRESS 경기가 남아 있었고 기존 경기 URL로 복원됐다. 이 실행에서는 로그인 후 lobby join으로 참가가 자동 정리된 것으로 관찰되지는 않았다.

명시 퇴장 직후 서버 확인: `battle-10`은 IN_PROGRESS, 방 10은 WAITING, A는 LEFT/left_at 존재, B는 HOST/left_at 없음이었다. 이후 일반 UI 재입장은 대기실로 갔다. 재참가 후 기존 경기 URL을 직접 열어 원래 경기를 마무리할 수 있었다. 즉 명시 퇴장이 완전한 기권 처리로 확정되는 것도 아니며, 화면과 경기 데이터의 생명주기가 일치하지 않는다.

## 재현된 추가 문제와 수정할 경계

1. **기존 참가자의 이어하기 진입 경로 부재.** `RoomCard.tsx:15`는 WAITING이고 만원이 아닐 때만 클릭을 허용해 STARTED 방의 기존 참가자를 구분하지 않는다. 로그인은 로비로 이동하며 RoomPage는 원래 활성 경기로 자동 이동하지 않는다. 기존 참가자/진행 경기 조회와 로그인·로비·대기실의 복귀 경로를 연결해야 한다. 일반 신규 입장 제한과 재접속 자격은 구분해서 검증해야 한다.
2. **명시적 퇴장 후 방/경기 상태 불일치.** `room/service.js`의 인원 부족 처리에서 방을 WAITING으로 바꾸지만 해당 matches 행은 IN_PROGRESS로 남았다. ‘잠시 나가기’와 ‘경기 포기’의 의미를 먼저 확정한 뒤 DB 참가·경기 상태·서버 초안·상대 화면을 같은 정책으로 처리해야 한다. 현재 코드를 기권 완료 또는 정상 이어하기 구현으로 간주하지 않는다. 이번 테스트에서는 정책을 바꾸지 않았다.
3. **지난 방 조회와 중복 퇴장 요청.** 여러 경기를 연속 진행하면 종료한 방 5/6/7을 새 경기 중 다시 조회하는 404와 중복 leave 409가 재현됐다. UI의 게임 진행/채점은 끝났지만 정상 요청 흐름으로 볼 수 없다. `RoomPage.tsx:569`의 await 이후 구독 등록과 `:879`의 공유 unsubscribe 저장, USER_JOINED/USER_LEFT의 요청 전 취소 검사 및 구독 해제 수명을 점검해야 한다. **구독 수명 경쟁이 원인 후보**이며 이 테스트만으로 한 원인으로 확정하지 않았다. 중복 퇴장도 단일 호출 경계로 분리해 재현/수정할 필요가 있다.

다음 수정의 회귀 기준은 주소 직접 입력 없이 기존 경기 복귀, 원래 경기 ID/시간/점수/빌드 횟수 유지, 미완료 경기 잔존 방지, 퇴장 이후 지난 방 조회/중복 퇴장 0건이다. 기존 점수·보상·닉네임·게임 규칙을 임의로 바꾸는 작업은 하지 않았다.

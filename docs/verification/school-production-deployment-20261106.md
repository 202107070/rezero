운영 서비스 설정은 `/home/user1/.config/systemd/user/rezero-backend.service`, 로그는 `/home/user1/rezero-runtime/logs/backend.log`다. 프론트/백엔드 소스와 프론트 빌드를 동일 버전 디렉터리에 준비했다. 브라우저 검증은 맥에서 빌드된 프론트를 `127.0.0.1:15175`로 실행해 **실제 학교 8080**으로 HTTP/Socket을 전달했다. 8080은 API 포트이며 정적 웹사이트를 서비스하는 포트는 아니다.

학교 PC에서 프론트를 실행할 때:

```sh
cd /home/user1/rezero-current
VITE_SYNC_BACKEND=true npm run dev
```

이는 브라우저 개발 실행 명령이다. 검증용 설치는 `npm ci --ignore-scripts`를 사용했으므로 Electron 실행 파일 설치까지 완료했다고 판단하지 않는다. Electron TypeScript 빌드는 통과했다. 백엔드는 이미 systemd로 실행 중이며 관리 명령은 다음과 같다.

```sh
systemctl --user status rezero-backend.service --no-pager
systemctl --user restart rezero-backend.service
tail -f /home/user1/rezero-runtime/logs/backend.log
```

## 백업과 데이터 대조

서버 안의 `/home/user1/rezero-backups/before-school-release-20261106-N251f3`에 운영 DB SQL, Valkey RDB, 원본 환경설정, 원본 Git/소스/미추적 파일을 담은 압축 백업과 SHA-256 manifest를 보관했다. 디렉터리는 0700, 비공개 파일은 0600이다. gzip 검사와 전송 아카이브 해시 검사를 통과했다. 백업 내용을 Git에 넣지 않았다. 실제 DB 복원은 수행하지 않았다.

적용 후 SQL 덤프의 원본 행을 대조했다. 기존 사용자 4행, 문제 168행, 아이템 40행, 칭호 2행, 경기 1행, 경기 문제 3행, 제출 2행, 순위 1행, 코드 기록 2행은 내용이 동일하다. 원본 환경설정 해시와 원본 체크아웃 status도 동일하다.

기존 방 1개와 참가 2행도 삭제되지 않고 남아 있다. 이 방은 기존 앱의 **6시간 초과 대기방 정리**가 목록 조회 시 동작해 CLOSED/LEFT 상태로 바뀌었다. 별도 DB 초기화·삭제·닉네임 마이그레이션을 실행하지 않았다. 운영 검증 계정 2개와 경기 3개는 실제 앱 흐름으로 추가했으며 기록을 삭제하지 않았다.

기동은 `PRESERVE_CHAT_ON_START=true`를 사용한다. 분리 환경의 전용 테스트에서 현재/과거 형식의 채팅 키와 TTL이 보존되는 것을 확인했다. 실제 최초 기동 직전 운영 채팅 키는 0개였다.

기동 전 Valkey 접속 검사에서 원본 `.env`의 비밀번호와 실제 무비밀번호 서버 설정이 일치하지 않았다. **새 버전의 비공개 환경설정에만** 빈 REDIS_PASSWORD를 지정해 실제 연결을 확인했다. DB/JWT/AI 설정은 원본 값을 유지했다. 이 작업에서 Valkey 서버 인증 설정을 변경하지 않았다.

## 설치·통합 검증과 발견한 수정

- 백엔드 단위 16개, 실제 JWT HTTP 1개, 프론트 14개, 기존 규칙 3개 통과: 합계 34개.
- 분리 DB·Valkey·API의 통합 묶음 6개 스크립트 통과: 채팅 기동 보존, 저장·복원, 실제 빌드, 닉네임 동시 중복 차단, 배틀 규칙/아이템, 확정 결과/Socket/중복 보상 방지.
- 맥과 학교에서 타입·프론트·Electron 빌드 통과. 기존 번들 크기/동적 import 경고 유지.
- 깨끗한 새 폴더 설치에서 lock에 누락된 `@emnapi/core`와 `@emnapi/runtime` 1.11.3을 보완했다. 기존 패키지 버전은 변경하지 않았다. 학교 `npm ci --ignore-scripts --no-audit --no-fund` 통과.
- **새로고침 후 상대 진행률 정지**를 운영 브라우저에서 재현했다. BattlePage가 방 입장 ACK를 기다린 뒤 경기 이벤트를 등록하고 있어 연결 교체로 ACK가 유실되면 구독이 생기지 않았다. 입장 요청과 이벤트 등록을 분리했고, 재접속 시 방 재입장은 유지했다. 같은 조건의 재검증에서 상대 진행이 Q2, Q3 및 마지막 문제까지 갱신됐다.
- **공백 정답 제출 차단**을 실제 V06 경기에서 재현했다. 서버가 정답을 숨긴 상태에서 공백 한 칸을 빈 입력으로 판단했다. 코드 빈칸의 입력 유무와 서버 정답 판정을 분리했다. 빈 문자열·미완성 입력·주관식 공백·로컬 정답 검증은 회귀 테스트로 확인했다. 재접속한 두 계정이 같은 공백 답안을 정상 제출/채점했다.

이전 분리 환경의 43개 실행 템플릿/자원 제한 검증 결과는 별도 기록이다. 이번 운영 단계에서 모든 언어의 전체 브라우저 경기를 다시 했다고 주장하지 않는다. 실제 운영 경기에서는 Python 실행 4종을 확인했다.

마지막 경기에서 실제 격리 실행 결과는 V06 사각형, LP03 `pass`, SV02 `####` 4줄, M05 `olleh`다. 첫 실행 후 빌드 2/3이 새로고침 후에도 유지됐다. 두 플레이어의 빌드 횟수는 분리됐다.

## 복구 경로

첫 배포 전에는 8080이 꺼져 있었다. 새 서비스와 이 작업에서 추가한 접근 규칙만 중단해 그 상태로 돌아가는 스크립트는 백업 폴더의 `stop-release.sh`다. 이 스크립트는 **작성만 했으며 실행하지 않았다**. 이전 서비스 설정과 버전 디렉터리도 보관했다. Linger의 이전 값은 no이므로 이를 되돌릴 때는 다른 사용자 서비스의 영향을 먼저 확인한다. DB를 삭제하는 `backend/database/rollback.sh`는 이번 복구에 사용하지 않는다.
